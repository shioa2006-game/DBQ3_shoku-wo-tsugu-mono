## 3. 順序と完了判定

### Step 0: 基準固定と最小再現

1. 各リポジトリのAGENTS.md、HEAD、既存差分を確認。別の作業者と同じツリーを同時編集しない。
2. Ch1–3で対象ごとの最小再現テストを追加・強化する。元診断の関数検証とブラウザ検証を区別して記録する。
3. D14を最後の一括作業にしない。攻撃・採掘・配置の合否が信用できる状態を先に作り、各修正と同時に回帰条件を追加する。

### Step 1: Ch1–3のみ修正

推奨順序（原則1 ID単位の修正＋対応テスト）:

1. D14の基礎整備とD01: 保存・戦闘復帰。
2. D05: 報酬保証。後続の進行検証の土台を守る。
3. D02: きのこの再生。
4. D06、D07、D20: 入力・残HP・長押し説明。
5. D09、D11: 作物の状態遷移・設計図の占有。
6. D10: 命中規則。対象別の回帰検証をまとめて行う。
7. D14の残り: 通しテストの弱い判定・救出待機の信頼性を見直す。

同じmain.jsへの変更でも、原因の異なる修正を大きな1コミットへまとめない。D14のテストは各IDのコミットに含めてよく、台帳から両IDに関連付ける。分割のために動作しない中間状態を必須にはしない。

### Step 2: Ch1–3の完了ゲート

- 10件それぞれの受入条件を満たし、未確認を成功と扱わない。
- `npm.cmd run test:ci`、`npm.cmd run build`、`npm.cmd run test:e2e` を実行して結果を記録。
- 通しテストだけでなく、通常入力で採掘・配置・攻撃・wheel・HP表示・報酬受領を確認。
- 修正後にNew Gameで作った同一版セーブで、戦闘中／勝利直後／報酬未受領／再生待ちの保存・復帰を確認。
- 全回帰失敗後の単独成功を「全回帰成功」へ書き換えない。失敗・再実行・環境差を残す。
- 対象外のカメラ、入力優先順位、保護時間、HUD配置などに意図しない変更がないことをdiffで確認。
- 修正・対応テストをコミットし、verification.mdにID→SHAと最終検証対象SHAを記録する。
- 引継ぎ文書の更新コミットも記録可能な形で残す。文書自身のSHAは自身に埋めず、Ch4–5の台帳で固定する。

上記を満たしてからCh4–5のコード修正へ進む。検証ができなければ未確認と理由を明記し、完了ゲート未達のまま「移植済み」にはしない。
ローカルの修正・検証が完了していれば、GitLab push待ちだけを理由にCh4–5の準備を止める必要はない。公開状況は別欄で管理する。

### Step 3: Ch4–5へ適用

1. Ch1–3の確定した計画・受入条件・コミット一覧をCh4–5のporting.mdへ、参照元のリポジトリ名・文書パス・SHA付きで記録。
2. Ch4–5の各IDを「共通原因あり／章固有へ適応／既存対処を検証／該当なし」に分類し、理由を記録。
3. Ch1–3の差分と回帰条件を読む。リポジトリ全体のmerge、main.js等の丸ごと上書きはしない。
4. 独立した小さな変更で依存・周辺差分も一致する場合に限り、個別コミットのcherry-pickを選択肢にする。既定はCh4–5の現行実装へ必要部分を適応する。
5. 各IDをCh4–5側のテストで検証。Ch1–3で成功していることは移植先の成功証拠にしない。
6. `test:ci`、`build`、`test:e2e` と第4・5章固有の確認を完了し、移植先のSHA・結果を記録。
7. 対応済み項目は「Ch1–3 SHA → Ch4–5 SHA」、既存対処済み／該当なしはその根拠とテストを記録して閉じる。

Ch4–5で共通修正の欠陥が見つかった場合は、同じIDでCh1–3へ戻す必要性を判断する。片側だけ追加修正したまま共通対応完了にしない。Ch6–7への適用、共通パッケージ化は今回の範囲外。

## 4. 受入条件と実装方向

以下は実装前の推奨。ユーザーが決定した対象範囲は固定し、未指定の時間やUI表現は実装時に根拠とともに確定する。

| ID | 推奨方向 | 必須の受入条件 |
|---|---|---|
| D01 | 戦闘状態を保存しないなら準備段階へ正規化。勝利状態の確定と保存を整合させる | 戦闘前・戦闘中の手動保存・勝利会話中・会話後の再ロードから再挑戦または次段階へ進める。戦闘も再開手段もない状態を残さない。報酬・素材消費が重複しない |
| D02 | 自然の採取地点で時間経過によるきのこ再生。初期案は1ゲーム日程度（数値は実装時に確定） | 採取→再生→再採取ができる。全消費後も空いている自然地点から再取得できる。建材・耕地・水・人を上書きしない。塞がれている間は延期等で安全に扱い、空いた後に再判定。New Gameで状態初期化、同一版セーブで待ち状態保持。無限即湧きや重複ドロップなし |
| D05 | 永続的な未受領報酬などで受取権を保持。アイテム追加の戻り値だけを直して終わらせない | 全満杯・一部だけ入る・複数種類・再会話・空きを作った後・再ロードで、欠損も二重受領もない。保存されない通常ドロップに逃がすだけでは不合格 |
| D06 | modal所有中のゲームwheelを破棄し、画面切替時の残留も防ぐ | インベントリ・収納・職業の書・会話・ポーズでスクロールしても閉じた後に選択が変わらない。通常時の選択とメニュー内スクロールは動く。開閉と同フレームの境界も確認 |
| D07 | HPの正値を表現できる最小限のハート表示 | HP0/1/2/3/4および最大HP26などの端数を区別・解釈できる。HP1が全emptyにならず、最大値超過や表示幅の揺れを起こさない。特定の四分割方式を要件にはしない |
| D09 | 段階変更時に成長進捗を適切に更新 | CROP1→2と2→3にそれぞれ意図した時間を要する。通常dt・大きなdt・住民加速・収穫・植え直しを検証。成長全体の所要時間が現在より延びる影響を章テストで確認。途中進捗の永続化は今回の必須追加機能にしない |
| D10 | 多重ヒット防止と攻撃者間のダメージ受理を区別。プレイヤー側被弾保護は維持 | 有効な攻撃間隔で命中できる。1回の攻撃が同一対象へ重複加算されない。味方の直前の弱い攻撃が主人公の攻撃を消さない。敵の接触で瞬殺されない。ボスの既存の無効段階は維持。具体的な無敵時間・攻撃識別方法は修正コミットに明記 |
| D11 | 通常配置と設計図配置で占有判定を共用 | 主人公・NPC・敵の占有中は配置せず素材も消費しない。占有解消後は配置できる。セル境界・足元・設計図完成判定を確認。D12の優先順位は変えない |
| D14 | 操作と直接対応する事後条件、状態ベースの待機 | 攻撃は対象HP差分／対象の死亡、採掘・種まき・配置は対象セルと所持品差分を検証。既存ドロップで合格しない。意図的な操作不成立でassertが失敗することも一時検証。章進行用の状態注入は残してよいが実操作テストと区別。routingの救出条件・初期状態を調べ、単なるtimeout延長だけで隠さない |
| D20 | ヘルプと初回採掘の案内に「左ボタンを押し続ける」を明示 | 新規開始時と再参照可能な説明から長押しが理解できる。攻撃／配置のクリックと混同しない。公式ブラウザテストのmouse down/upで木材取得を確認。追加の採掘ゲージ・新UIは必須にしない |

## 5. 記録・コミットの運用

実装ごとに台帳へ以下を記入する。

1. 原因と守るべき挙動、変更したファイル／関数。
2. 実装で決めた仕様（再生時間、満杯報酬の受領方法、命中規則等）。
3. 修正コミットと、追加／更新したテスト。
4. コマンド、対象SHA、環境、結果、再実行、未確認、必要な画面証跡。
5. Ch4–5側で変える必要のある章データ・呼出経路・既存対処。

台帳に「対応済み」とだけ書かない。機能コード・回帰テスト・仕様記録を対応付ける。画像や大量ログは各リポジトリの同ディレクトリ配下 `evidence/<ID>/` へ必要最小限を保存するか、恒久的なCI/MR artifactへリンクする。個人の絶対パスや一時セッションIDだけを引継ぎ根拠にしない。

Ch4–5への引継ぎ時点でこの計画をSHA付きで固定する。Ch4–5台帳内のローカル受入条件はその時点の写しとして扱い、方針変更は変更日・理由・両リポジトリへの反映状況を記録する。
push・公開は各AGENTS.mdに従い、ユーザーによるpush後に確認する。今回の文書作成ではcommit・push・公開を実施しない。
